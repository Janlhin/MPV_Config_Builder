这些结论都是**实测出来的**，不是看代码猜的。每条都写清了「怎么验的」，
因为下次遇到类似问题，判据比结论更有用。

## mpv 本身的行为

| 结论 | 怎么验的 |
|---|---|
| **8 位颜色是 `#AARRGGBB`，透明度在最前** | 11 个默认值定案：`sub-back-color=#AF000000` 按"透明度在后"会变成全透明的暗红，说不通。**我一开始判断反了**，是数据把我纠正过来的 |
| **`#` 之后一律算注释** | 手册原文。所以颜色值必须写成 `"#RRGGBB"`（带引号）；本工具生成时自动加引号，并在体检里拦 |
| **光写选项名 = `=yes`** | 手册原文。解析器照此处理 |
| **`vf=` 路径含空格必须整体加引号** | 没加引号时 mpv 直接报 `Error parsing option vf (option parameter could not be parsed)` |
| **未改动的行可以逐字节原样写回** | 用真实的 148 行 `input_uosc.conf` 验过：解析 → 渲染完全一致 |
| **include 链里引的都是 profile** | 用户那份 `mpv.conf` 引的两个文件全是 `[小节]`，所以跟随 include 不会污染全局值 |

## 这个工具自己的行为

| 结论 | 怎么验的 |
|---|---|
| **融合脚本可用** | 真实 mpv 播 lavfi 测试源，错误行 0，滤镜链/首帧/EOF 与原版脚本一致。（原版就有的 `Frame requested during init!` 警告来自 k7sfunc 脚本风格，不是我们的问题） |
| **键位编辑生效** | 改过的键在真实 mpv 的 `input-bindings` 里确认生效；被注释的条目确实不生效 |
| **合并写入曾每次新增一个抬头块**（已修） | 真机写入留下的证据：`mpv.conf` 被写两次 → 文件末尾两个一模一样的 `# 由 MPV Config Builder 写入 #` 块。修复后连写多次仍只有 1 个块（有回归测试） |

## mpv-lazy / 下载

| 结论 | 怎么验的 |
|---|---|
| **完整包是分卷，且 `-noVS` 包不能要** | 实测 release：`noVS`（47 MB，**无 VapourSynth**，补帧全废）／`vsNV.7z.001+002`（合计 2771 MB）。**"选体积最大的"会挑错**。分卷是否齐全要读 **7z 文件头**判断（三个字段全 `0xFFFFFFFFFFFFFFFF` = 后面还有卷） |
| **uosc 的包里 11.3 MB 是别的平台的二进制** | 实测 `uosc.zip`（18 MB / 45 个成员）：`ziggy-darwin` 5.71 MB + `ziggy-linux` 5.59 MB，Windows 用不上；但 `ziggy-windows.exe` 是它自己要用的，必须留 |

## 界面 / 前端

| 结论 | 怎么验的 |
|---|---|
| **原生 `<datalist>` 的气泡没法跟主题** | 它由浏览器 UI 层绘制：**不在 DOM 里**、**不吃页面 CSS**、连 `Page.captureScreenshot` 都抓不到 → 只能自绘。判据：「能不能被截图抓到」≈「在不在页面渲染层」 |
| **加了自定义 class 却没处理它继承的按钮样式** | 顶栏导航项写成 `class="btn small topnav-link"`，再写 `.topnav-link{border:none;background:none}` —— **一行都没生效**。CSS 权重同为 (0,2,0) 时看谁在后面，而 `.btn.small` 在后面。**看截图只会以为"样式没调好"，是 CDP 读 `getComputedStyle` 才定位到根因** |
| **浏览器里开发看不出的错，只有换传输时才现形** | 把前端传输换成 stdio 时，发现 4 处漏网的直连 `fetch('/api/...')`。它们在浏览器里**完全正常**，只有 stdio 通道（没有 HTTP）才会静默失效。**只测一种传输，等于没测「传输可替换」这件事** |
| **页面的「剩余汉字」里混着后端返回的数据** | analyze 页前端文案做到 0 之后，`verify.py i18n` 仍报剩 2 字。用 CDP 把切英文后**所有含汉字的文本节点** dump 出来，抓到是 `<option>profiles.conf（profile 集合） · 1612 B</option>` —— 来自后端的文件描述，**根本不是前端文案**。判据：总数不许只看数字，要把残留节点 dump 出来归因；归到后端就转 T14，**不要拿前端词典去盖后端的字符串**（那是把别处的债记在自己账上） |
| **`data-i18n-ph` 会被词典兜底覆写回中文** | 读 `i18n.js` 的 `walkDict`：它处理 `placeholder` / `title` 属性时，按**记录的原文**重算并重设，而属性分支**没有**像文本节点那样跳过 `[data-i18n]`。于是 `apply()` 刚写进去的英文，会被还原成中文（除非该串同时在词典里）。结论：内页未标记的静态文案一律走词典，**别单独指望 `data-i18n-ph`**。（这条是读确定性代码路径得出的，没再单独做运行时验证） |
| **运行时拼的字符串要过两道关，只修一道等于没修** | hell 页 toast「已读取 N B」切语言后变成「已Read N B」。两道独立的坑：① 改成 `I18N.t(key, vars)` 只修了**英文态渲染**这条路径；页面**加载时**（中文态）渲染进 DOM 的字符串，切语言时仍会被词典兜底**重扫**——「已读取」没词条，短条目「读取」→ Read 切坏了它中间。补词典长条目（长匹配优先）才挡住。② sizeHint 这类渲染完就不变的，要监听 `i18n:change` 重刷（`setLang` 派这个事件就是给动态文案用的），否则永远停在加载时那门语言。判据：`verify.py i18n` 报的每页残留数 + CDP dump 残留节点归因，**两个数字都对上 0 才算完** |
| **「切后剩 0 汉字」只测量了切语言那一刻，操作后才出现的字符串不在测量范围内**（2026-10-14 downloads 轮实测） | downloads 页 `verify.py i18n` 报 292 → 看着"差不多了"，但那一数字是**点完切换按钮立刻**数的 DOM。真正做深一页要把两条渲染路径分别过一遍：**加载时渲染的**（列表、状态行——i18n:change 重刷覆盖）和**用户操作后才渲染的**（confirm 对话框、toast、按需求解的安装计划 / 链接校验面板——verify 永远看不到）。downloads 轮把后者也全部改走 `I18N.t()` 才敢叫"前端归零"；hell 轮当时漏了约 8 条 confirm/toast（已登记 TASKS.md 遗留项）。判据：**一页做完的标准不是 verify 数字归零，是 grep 一遍该页所有面向用户的字符串、每条都能说清走的是哪条翻译路径** |
| **通用短词条会误切后端字符串，但解法不是去加长词条盖它**（2026-10-14 downloads 轮实测） | uosc 的 `note_extra` 切英文后变成「会Write fonts/ 与 scripts/uosc/ 一整棵目录树；卸载时逐个File校验后删」——「写入」「文件」是给前端界面用的通用词条，按子串匹配命中了后端文案。**这不是谁加了坏词条，是兜底机制的固有代价**；给后端字符串补长词条就是「拿前端词典盖后端的字符串」（踩过的坑第一条判决），债会越记越乱。正解是 T14：后端按当前语言直接返回英文，兜底层自然不再参与。判据：CDP dump 归因时看到**中英混杂的后端串**，转 T14，不动词条表 |
| **「构建时取一次文本」会把语言冻在加载那一刻，重渲染写回去还是旧语言**（2026-10-14 advanced 轮实测） | advanced 页侧栏分区原来在 `buildSections()`（页面加载时跑一次）里就把 `I18N.t()` 求好存进对象，`render()` 重渲染时直接写这个存好的值 —— 切语言后整页重刷，侧栏名和分区副标题**原地写回中文**，而同一帧里的 `secTitle`（渲染时取键）却是英文，一屏中英混排。修法：**存键不存文本**（`nameKey`/`subKey`），渲染时经 `secName()/secSub()` 现取。判据：往返探针（中→英→中→英）必须每帧都干净；只测「切过去那一帧」会漏掉这类**重渲染路径**的 bug——它正是 i18n:change 机制存在的理由 |
| **切语言重绘要用缓存响应，不能重新请求——否则丢用户未保存的编辑**（2026-10-14 keys 轮实测） | keys 页的 `i18n:change` 重绘，最自然的写法是重新 `load()`（重新拉 `/api/keys` 再渲染）。但那会用服务端响应**覆盖 `KEY.rows`**，用户改了一半没保存的键位编辑被静默丢弃——而且丢得毫无痕迹（界面只是「刷新」了一下）。修法：`load()` 拆成取数 + `renderMeta(r, f)`，响应存进 `KEY._last`，重绘只走缓存渲染函数（`renderMeta` / `renderPromote` / `renderRows` / `renderRef`），一个请求都不发。判据：**页面持有用户未提交状态时，重绘必须走缓存**；探针要先制造一个未保存编辑、切语言、再检查编辑值是否原样还在（keys 轮已将此探针跑过，编辑值存活） |

## 测试 / 验证方法（最容易吃亏的一类）

| 结论 | 怎么验的 |
|---|---|
| **手挑的测试用例，挑漏的地方就是漏掉的差异** | 把 17 条冲突规则从 if 链改成规则表时，55 个手选用例 + 全套测试**全绿**，改成 4699 组**系统枚举**后立刻抓到一个真 bug。原因是手选用例**全是「两个 target 同时开」**，恰好漏了「只开一个」。**结论：高风险重构的判据是系统枚举，不是手选用例** |
| **报错和成功同时出现时，先怀疑检查本身** | 验收 Electron 时用 `tasklist /FI "IMAGENAME eq X.exe"` 数后端进程，**永远返回 0**（Windows 引号：cmd 里是一个参数，Python 传 list 时拆成三个）。现象极具迷惑性 —— **同一时刻后端明明活着**，只有这条检查在报"没有后端进程"，我差点去改 spawn 逻辑。**一个永远不会成功的断言比没有断言更糟：它会让你去修不存在的问题** |
| **字符串匹配会撞上文档串** | 用 `"http.server" in 源码` 判「stdio.py 有没有依赖 HTTP」→ 报了违规。实际是它**文档串里那句「这个模块不许 import http.server」**被当成了违规本身。**这种检查比没有还糟：它逼你去删一句正确的注释。** 改成 AST 判据 |
| **「文件都在」不等于「能用」** | 打包后 exe 起不来：产物存在、体积正常、`data/`+`static/`+`*.md`+`LICENSE` **全都在包里** —— 崩在 import 阶段，连一行输出都没轮到打印。**只查文件的检查会全绿放行** |
| **`.bat` 带 UTF-8 BOM 会炸，而且只在双击时炸**（2026-10-09 实测，**推翻了原约定**） | 双击打开是全新控制台（代码页 936），cmd 把开头的 `EF BB BF` 当命令的一部分 → `'@echo' 不是内部或外部命令`（**3/3 稳定复现**），`@echo off` 没执行、echo 关不掉、`rem` 注释被当命令跑。**最坑的是时好时坏**：同一会话里跑过 `chcp 65001` 之后代码页已是 65001，BOM 被当 U+FEFF 忽略 —— **在终端里试是对的，双击就是坏的**。结论：`.bat` 用 UTF-8 **无 BOM** + CRLF，中文靠 `chcp 65001`（放第二行），**开头别放大段中文注释** |
| **cmd 会按控制台代码页预读 `.bat` 头部** | 把 `chcp 65001` 放到第一行也没用：中文 `echo` 照样被截断成 `'文输出_OK' 不是内部或外部命令`。原因是 cmd 用**读取时的代码页**解码，且会预读一段 —— 而预读发生在 chcp 生效之前。**结论：`.bat` 开头保持短且纯 ASCII，说明文字放文档** |
| **`where py` 成功 ≠ `py -3` 能跑** | `py.exe` 可以在系统里存在、而它管理的运行时列表是空的或不含 3.x —— 这时 `py -3` 退出 103（`No suitable Python runtime found`），**而 `where py` 依旧返回 0**。于是「找到了就用它」的脚本永远走不到 `python` 兜底，用户只看到一句看不懂的英文报错，而本机明明装着能用的 Python。**结论：判断"在不在"不够，必须真的跑一下解释器** |
| **实机检查里固定 sleep 是 CI 间歇红的来源（等条件，别等时长）** | docs-only 提交在 CI 上**红过一次**，红的还是与改动完全无关的顶栏检查。翻日志：`cmd_topnav` 导航后固定等 2.2s 就探针 `.topnav`，而顶栏是 **JS 注入**的，注入完成时刻随机 —— 本机快所以 8 次全绿，CI 慢就偶发落空。**同一检查在两次绿之间夹一次红，这种「间歇性」本身就是特征**。修法：`uidriver.wait_for()` 轮询就绪条件（`.topnav` 有 3 个子节点）至多 10s，再探针。**判据：检查红过一次就要翻全部运行历史，确认是竞态还是真缺陷；修完在报红的那个环境复测** |
| **宿主自己是 Electron 应用时，spawn 出来的 electron.exe 会退化成纯 Node**（2026-10-10 实测） | 验证脚本在**宿主环境**（WorkBuddy 本身是 Electron 应用）里 spawn electron.exe，子进程继承了宿主设的 `ELECTRON_RUN_AS_NODE=1`，于是走 Node 分支：`require('electron')` 返回路径字符串、`app` undefined、调试端口永远不开 —— **现象极像 main.js 写错了**，实际代码一行没错。main.js 的 require 顺序排查了半天，真正根因在环境变量。修法：spawn 前 `env.pop("ELECTRON_RUN_AS_NODE", None)`（`cmd_electron` / `cmd_packaged` 两处，后者原本没传 env 更隐蔽）。修完 `verify.py electron` 19/19、`verify.py packaged` 13/13 全绿。**判据：怀疑代码之前，先在跑验证的同一环境里 `echo $ELECTRON_RUN_AS_NODE` 查环境；「代码没问题但跑不起来」优先排查继承来的环境变量** |
| **GPU 进程崩溃会让 electron 检查整个红掉，而且现象极像代码坏了**（2026-10-14 实测） | 同一套 electron 检查四天后全红：窗口创建成功、调试端口也开了，但 CDP 一连上就 `ConnectionResetError`。根因不在代码：本会话环境里**独立 GPU 进程必崩**（`exit_code=-1073741819` 即 0xC0000005，重试 9 次后 Electron `FATAL: GPU process isn't usable. Goodbye` 整个退出）。**证据链**：`verify.py packaged` 跑的是 4 天前的旧 asar（压根不含新改动）以同样方式红 → 红与代码无关。三种绕法实测：`--disable-gpu` **无效**（GPU 进程照崩）；`--no-sandbox` 能活但削弱安全面；**`--in-process-gpu` 单独可解**（GPU 进程并在主进程内，不单独起就被沙箱限制不到），且不改变被验证的行为——这些检查验的是页面渲染 / IPC / 导航，不是 GPU 性能。已加进 `cmd_electron` / `cmd_packaged` 的 spawn。**判据：CDP 类检查「窗口起来了但一连就断」，先看 app 输出的 GPU/FATAL 行，再怀疑页面代码** |
| **git 钩子无法直接写成 .ps1：解释器拒绝 -File 无扩展名文件**（2026-10-14 实测） | 想把 `.githooks/pre-commit` 从 sh 改成 PowerShell 脚本时发现：Git for Windows **会**识别 shebang 并把调用转过去，但它以 `-File <钩子完整路径>` 方式执行，而 `-File` 要求文件必须带 `.ps1` 扩展名；git 又只认固定名 `pre-commit`（无扩展名）——两头夹死，此路不通。936 代码页下的实测报错（转码后）：「-File '...\pre-commit' 失败，因为文件没有 '.ps1' 扩展名。必须指定有效的 PowerShell 脚本文件」。结论：钩子保持 sh，登记为 Pwsh-only 基线的文档化例外（DECISIONS.md Q-002、AGENTS.md §2.4）；钩子里不放逻辑，只当分发器。**判据：看到「-File 失败，因为没有 .ps1 扩展名」这类报错，别去改 shebang——shebang 已经生效了，卡的是扩展名校验** |
| **Python 3.13 的 `subprocess text=True` 解码失败不抛异常：读取线程静默死掉，stdout=None**（2026-10-14 实测） | `subprocess.run([...], capture_output=True, text=True)` 在 3.13 里由**读取线程**解码；输出含非 UTF-8 字节（本机 `tasklist` 输出按控制台代码页 936 编码，环境里有中文进程行就中招）时：线程把 UnicodeDecodeError 打到 stderr 后死掉，**主线程的 run() 正常返回、stdout=None** —— `try/except` 根本拦不到，下游在毫不相干的地方撞上 `AttributeError: 'NoneType' object has no attribute 'splitlines'`。同一时刻 stderr 里还飘着一个"没有调用栈上下文"的解码报错，极具迷惑性。修法：读**进程/控制台输出**的 subprocess 一律显式 `encoding="utf-8", errors="replace"`（只做 ASCII 匹配时对判据无损），并对 `stdout` 做 `or ""` 兜底。**判据：`text=True` 的调用点拿到 None 别怀疑 subprocess 坏了——是读取线程解码炸了；这类崩溃永远"时有时无"，跟着环境里有没有非 ASCII 进程行走** |

| **断点续传不能只看「本地有没有字节」**（2026-10-20 审计） | 旧实现只要 `.part` 有残留就发 `Range` 并 `ab` 追加；镜像/CDN 忽略 Range 返回 200 全文时，包体前段重复、后段错位 —— 后面的 sha256 校验再严也救不回来。修法：只有 `206` 且 `Content-Range` 起点等于本地长度才续传，否则截断重下；`.part.meta` 记 url/etag/总长，没有可信元数据就不敢续。**判据：续传属于"外部承诺"，必须验证对方的应答，不能假设 Range 被遵守** |
| **`Path("")` 在 Windows 上等于当前目录**（2026-10-20 审计） | 空 `target` 走 `Path("")` → `is_dir()` 恒真 → "目标目录不存在"的守卫失效，配置写进进程 CWD（Electron 下是 `webui/`）。修法：空串直接拒绝，并让目标必须过 `_looks_safe_target`（拒盘符根 / 仓库 / 用户主目录）。**判据：任何"用户没填"的路径参数，先判空再判存在，别让 `Path("")` 替你做决定** |
| **`Path.write_text()` 在 Windows 写 CRLF，而且不是原子写**（2026-10-20 审计） | 项目约定换行一律 LF，但 `write_text` 的默认 `newline` 会按平台转换；同时它是"先截断再写"。两者叠加：既违反 §2.3，又可能留下半截文件。修法：统一 `textio.write_atomic`（显式 LF + 临时文件 + `os.replace`）。**判据：写用户文件不要用 `Path.write_text`——它不是"简单写一下"，是"换个平台就变行为、崩一次就毁文件"** |
| **实机检查触发主操作按钮，会真写用户的配置文件**（2026-11-08 hotkeys 轮实测） | 快捷键检查要按 Ctrl+S 验证「按钮真的被点了」，而 basic 页 `boot()` 在本机有 mpv-lazy 时**会自动把 target 填上** —— 打桩前按一次 Ctrl+S 就真写了一份 `mpv.conf`。修法：检查开头把 `API.basicApply` / `API.keysSave` 换成返回 `{ok:false}` 的桩（与 status 检查 stub `API.status` 同一手法），按钮点击、事件链、defaultPrevented 全都真实发生，只有落盘被拦。**判据：实机检查只要会触发"写"语义的动作，先盘点该动作的数据流到哪一层，把最外层 I/O 换成桩；「页面是空的所以不会真写」不算理由 —— 页面自己会探测环境并自动填值** |
| **grid-rows 揭示动画的三连坑：收起后永远剩一条缝，残差就是「漏算的那层盒」**（2026-11-08 motion 轮实测，探针抓 `getComputedStyle().gridTemplateRows` 的解析值） | `grid-template-rows: 0fr↔1fr` 做展开动画，收起时轨道停在 18px→20px 不归零。三个独立的坑叠着：① 轨道项的 **margin 计入 min-content 贡献**——`overflow:hidden`+`min-height:0` 只清零内容下限，清不掉 margin（残差=margin 值）；② 同理 **padding 也计入**——`height:0` 的收缩不含 padding（残差=padding 值），所以裁剪层必须是无 padding 的裸 div，视觉样式（背景/内边距）住进裁剪层**里面**的第三层；③ 改完模板发现残差变了但没归零——**旧规则没删干净**（`.expand` 的旧 padding 规则还在生效，残差正好等于它）。修法：三层结构 `.expand（容器，水平缩进用 padding）> 裸裁剪层（overflow:hidden+min-height:0）> .expand-body（padding+背景）`。**判据：这类「差一点」的布局 bug 别靠肉眼，`getComputedStyle` 的解析值（gridTemplateRows 的 px、各层 offsetHeight）直接告诉你残差是谁；残差的数值本身就是嫌疑层的尺寸** |
