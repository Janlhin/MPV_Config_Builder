### ⚠ 为什么 i18n 机制（3）要排在界面打磨（4）前面

直觉上会想「先把界面做好看，再弄多语言」。**但那样会返工一遍**：
先把快捷键、右键菜单、状态栏都用中文写死，等做 i18n 时那些新文字**又得再抽一遍**。

正确顺序是**先搭机制、再打磨** —— 新功能一开始就按 i18n 的规矩写，一步到位。

注意第 3 步**只搭机制**（框架 + 切换 + 一个页面当样板），不是把 1098 处翻完；
翻完是第 5 步。

## 一、界面打磨那批（顺序里的第 4 步，展开说）

现状：**能用，但有明显的"套壳感"**。用户原话：「快捷键 配置体检这种体验不是很好」——
不是这两个功能做得差，是它们**不像"软件的一部分"**。

| 缺什么 | 现状 | 影响 |
|---|---|---|
| **键盘快捷键系统** | 基本全靠鼠标 | 改一个选项要点半天 |
| **右键菜单** | 没有 | 想「恢复默认 / 复制选项名 / 看手册原文」无从下手 |
| **底部状态栏** | 没有 | 看不到当前配置文件路径、改动几处、后端是否活着 |
| **后端挂了有提示** | **白屏，什么都不说** | 用户以为软件坏了 |
| **加载中的进度** | 有些地方直接空白 | 读配置、扫描 shader 目录时像卡死 |
| **自绘标题栏** | 系统默认灰条 | 一个改动就能让"套壳感"少一半 |

## 二、功能缺口

| 项 | 说明 |
|---|---|
| **本地 HTTP 的 Origin 校验** | 浏览器里别的网页能打你本机的服务端口。stdio 模式没这问题，网页版有 |
| **VS 插件一键安装** | 往 VapourSynth 目录装插件。风险较高（写到 mpv 配置目录外面） |
| **`prefers-reduced-motion` 适配** | 无障碍缺口。小活，不管加不加动效都该补 |
| **界面动效** | 要不要加、加哪些 —— 一直没拍板 |

## 三、已定的约定（不是待做，是规矩）

### 版本号怎么涨

**唯一来源是 `core/schema.py` 的 `VERSION`。** 改完跑 `py tools/sync_version.py`
把版本刷进 `electron/package.json`（那边打包时要用）。忘了跑也没事 ——
`tests/test_version.py` 有一条测试钉住两边相等，会红。

| 什么时候 | 怎么涨 | 例 |
|---|---|---|
| 小更新（改文案、修 bug） | 最后一位 | 0.1.0 → 0.1.1 → 0.1.2 |
| 大更新（加功能） | 中间那位 | 0.1.x → 0.2.0 |
| 觉得能正式推荐给别人了 | 第一位 | 0.x → 1.0.0 |

所以 **0.x 阶段就是「还在做」的意思**。

> 2026-09-14 顺带定：**界面只显示软件版本**，不再显示「2.0」。
> `APP_VERSION = "2.0"` 那个常数留着，但只为旧界面服务 —— 那份 2026-10-09
> 已移出仓库、归档到 `..\MPV_Config_Builder_legacy\`，而它 import 的是**仓库里的**
> `core.schema`，所以这个常数**不许删**（`tests/test_version.py` 钉着）。
> 主界面测试会拦着不让它用。生成的配置抬头也从
> `# MPV Config Builder 2.0` 变成了 `# MPV Config Builder`。
> 合并写入不受影响 —— 它认的是另一条标记「由 MPV Config Builder 写入」。

### 界面里不许直接 fetch `/api/`

传输是可替换的（HTTP / stdio）。页面里任何一处直接 `fetch('/api/...')`
都会在 Electron 下静默失效。全部走 `API.xxx()`。
由 `tests/test_frontend_transport.py` 静态守着。

## 四、已拍板的决定（2026-09-14）

下面每条都附了当时的理由 —— 记着是为了**下次别又问一遍**。

### 1. 给谁用 → **发出去给别人用**

⚠ 这条把优先级全改了。「自己用」时可以不管的事，现在都变必须：
README 中英双版、界面文案排查、后端挂了要有提示、未签名的交代、英文界面。

### 2. 原版 mpv → **做成同等支持**

改三处：README 定位（"原版也能用，mpv-lazy 用户更方便"）、自动探测的说明、
组合预设里标出哪些依赖 mpv-lazy 的 shader 包（原版用户选了会是空的）。

### 3. 初始化引导 → **只在第一次出现**

进去后就不再问；想要时能从菜单里手动打开。
内容：先问「你要干嘛」（从零开始 / 改现有配置 / 只看体检）→ 再展示检测到的
多个 mpv 目录让你确认。

> 现在会**挑一个就停，从不告诉你还有别的** —— 用户机器上
> `C:\Program Files\mpv-lazy\portable_config` 和 `%APPDATA%\mpv` 都存在，
> 但程序只用了第一个，界面上不说。

### 4. `产品规划与路线图.md` → **拆，并把开发记录里有用的抽出来**

实测 1109 行里，真正给用户看的只有 §一 + §二（约 123 行）。
⚠ 那 17 条冲突规则「依据哪句 mpv 手册原文」**只记在这份文件里**，
代码注释里没有 —— 拆的时候必须先抽出来。

### 5. README → **合并成中英双版，只留简介**

英文当默认（`README.md`），中文放 `README.zh-CN.md`。
`README.txt` 删掉，里面的目录结构、打包步骤等详细内容进 `docs\`。

### 6. `tools\` → **合并成 3~4 个**

17 个文件、3000+ 行 → `verify.py`（验证）/ `build.py`（构建）/ `uidriver.py`（公共库）。
其中 11 个是 `check_*.py` 这类"为了证明做对了"写的验证脚本（`check_ui.py` 一个就 501 行）。

### 7. shader 扫描 → **改成列表，不做全盘扫**

用户确认 shader 都在标准的 `portable_config\shaders\` 和 `vs\` 下。所以：
- 要做「扫描源改成列表」（自动探测 + 手动添加多个目录）
- **不必做**「读 mpv.conf 看实际引用路径」（他的都在标准位置）
- **不做全盘扫**（慢、会扫到无关的、且 mpv 未必加载得了）

### 8. 代码签名 → **不买**

不是"什么都不做"，而是要给未签名的安装包一套交代（见顺序表第 11 步）：

| 要做 | 为什么 |
|---|---|
| README 写清会看到什么、怎么继续 | 不写的话用户以为是病毒 |
| 配那个对话框的截图 | 光用文字描述，用户对不上号 |
| 发布 SHA256 校验值 | 未签名时唯一能验证"没被换包"的手段 |
| 提醒国产杀软可能报毒 | 未签名的打包 exe 在国内比 SmartScreen 更常见 |
| 从 GitHub Releases 发布 | 别放网盘 —— 更容易被换包 |

⚠ 打包时**不要开 UPX**（杀软误报率显著提高），配方里已经关掉了。

### 9. 英文界面 → **一定做**

用户原话：「英文界面一定做，README 也做」。

**中文是默认**（用户母语），英文加上，界面上有个地方能切。

实测工作量：

| 部分 | 条数 |
|---|---|
| 界面文字（HTML + JS） | 约 1098 条 |
| 后端文案（Python） | 149 条 |
| 选项说明 | **726 条**（平均 140 字，共约 10 万字） |
| 分类名 | 24 个 |

**⚠ 选项说明那块不用翻译**：那 726 条中文是从 mpv 官方 `options.rst` 翻过去的，
直接取官方英文原文即可 —— 比翻译准，也比翻译省事。来源跟中文那份对称
（中文来自 `mpv_doc-CN`，英文来自 mpv 官方手册）。

**i18n 用「抽成 JSON + 运行时切换」，不做两套 HTML。**
两套 HTML 意味着 9 个页面变 18 个、改一处要改两遍 —— 就是本项目一直在避免的"存两份"。

### 10. 英文界面下的 4 份中文文档 → **最后再翻**

在那之前：切到英文时文档页照常显示中文，**顶部提示一句**
「这几份文档目前只有中文」。不装作有英文版，也不隐藏。
