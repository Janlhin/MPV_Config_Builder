> **审计对象**：`MPV_Config_Builder`
> **基线**：`master` HEAD `c65d6cf`，审计时工作区干净；**修复前** 650 项测试

## 〇、一句话结论

**core 的分层是真的（零反向依赖、零环），但「应用层」与「传输层」被塞进同一个叫 `server.py` 的文件里，前端状态与渲染也没有边界——架构靠文档和门禁维持，而门禁恰漏掉了自己最关键的两条（800 行、版本号唯一来源）。**

综合健康度：**2.8 / 5**。领域层是一套好架构；应用层与前端是一套"靠纪律维持的架构"，而纪律最关键的判据恰好没被门禁覆盖——它正按预期方式腐化：不是变乱，是变胖。

两条路径确实汇合在 `dispatch`。失败语义被刻意对齐：POST body 解析失败都补 `{}`（`server.py:1268` / `api.py:208-210`），错误都映射到 `detail`（`api.js:62-63`）。

### 1.5 i18n 链路

```
① 静态   HTML data-i18n/-html/-title/-ph → i18n.js apply() → DICT（zh 398 / en 398 键）
② 运行期 state.js / api.js 用 I18N.t(key,vars) → setLang() 派 'i18n:change' → 各页重绘
```

断点明确：**③ 是补丁不是机制**（子串替换会误切后端串）；**④ 是结构性缺口**——后端无语言感知，前端词典又被明令不准去盖。

## 二、清晰度评估

### 2.1 分层边界：core 干净，webui 的"层名"与"层内容"不符

- **事实**：core 对上层 import = 0，core 内部无环；但领域层里有界面 DTO——`core/schema.py:961-979 value_info()` docstring 写着"给界面用的值域信息"，返回 `{suggest, options, open}`，其中 `open` 是渲染决策字段；`schema.py:981-1010 db_ui_item()` 产出 `kind:"db"` 的界面结构。
- **事实**：应用逻辑住在"服务器"文件里——`server.py` 161-1203 是 39 个 `api_*`，1209-1270 才是 HTTP 适配，1279-1328 是开浏览器窗口。
- **判断**：纵向分层成立且守得住，是全项目最扎实的一块；横向分层**名义存在、物理不存在**。stdio 模式启动时也会把 `http.server` 加载进来（不监听端口，但依赖是真的）。结论：**不是 core 被污染，是应用层被传输层绑架**。

### 2.2 模块职责：4 个上帝文件

1. `core/schema.py` 1104 行 ≥ 6 件事：常量、`settings.json` 读写、`PARAMS`/`NATIVE_OPTIONS` 大表、磁盘扫描、mpv 值语法、值域校验 + DB→UI 映射。
2. `webui/server.py` 1332 行 = 39 接口 + HTTP 适配 + 后台任务表 + 开窗。
3. `webui/static/state.js` 1414 行 / 75 个顶层声明 / 9 个主题：状态、本地记忆、网络、diff 视图、选项行渲染、自绘组合框（289 行）、字幕预览（201 行）、输入校验、抽屉、shader 链、VPY 融合。
4. `webui/static/api.js` 601 行 = 传输抽象 + 转义/着色/toast + 顶栏/主题/语言注入 + 状态栏 + 右键菜单，还**给 `API.invoke` 打猴子补丁**。

**判断**：没有传统上帝对象（`APP` 是数据结构），但有 4 个上帝文件；前 5 大源文件占全部源码约 40%。`schema.py` 最该拆（只有"UI DTO 工厂"越界）；`api.js` 最危险——"零 HTML 改动"的取舍使它事实上成了 `common.js`。

### 2.3 传输抽象：分发是真的共用，"门面"被绕过一半

- **事实**：同一个 `dispatch()`：HTTP 在 `server.py:1247,1269` 调，stdio 在 `stdio.py:125` 调；行为一致性有测试钉住（`test_api_dispatch.py` 27 例、`test_stdio.py` 32 例）。
- **事实**：处理器全在 `server.py`，`api.py` 只存字符串属性名；换 HTTP 框架要动 39 个函数的家。
- **事实**：前端"必须走 API.xxx()"只做到一半——`api.js` 定义 34 个具名方法，但页面 + state.js 里 `API.get/post('/api/…')` **字面量直调 26 处**，具名方法调用仅 21 处（约 55% 绕过门面）；另 16 个具名方法全仓无人调用；**没有测试**校验 `api.js` 的 URL ↔ `api.py` 的 ROUTES 一一对应。
- **判断**："共用一套分发"是真的，教科书级；但抽象只到分发层，没到处理函数层。前端门面是软约束：能过 fetch 白名单，却不阻止手拼路径，拼错只在运行时 404。

### 2.4 前端状态管理：单一全局可变对象 + 隐式渲染订阅

- **事实**：`state.js:12-35` 顶层 `var APP`（24 字段），注释自承"用 var 是为了挂到 window 上方便调试"。
- **事实**：`APP.x =` 直接赋值约 30 处，无单一写入口；通知双轨（`APP.onStateChange`/`onRender` + 全局事件 `'i18n:change'`）；渲染函数改业务状态（`renderIssues` 里 `APP.conflicts = …`）。
- **事实**：另有模块级单例：`DIFF`、`comboPop/comboInput/comboActive`、`_drawerItem`、`_previewTimer`、`SB`；DOM 写入 state.js 46 处 + HTML 内联脚本 66 处。
- **判断**：这是"约定式全局 store"，靠 `typeof fn === 'function'` 防御式判断规避调用顺序——在 `file://` + 无打包器约束下是合理取舍。风险不是"乱"而是**不可观测**：谁能改 `APP`、改完是否重绘全凭自觉；三页共用 state.js 时，后挂的 `onRender` 会覆盖前面的。没有单向数据流，也没有单一写入口——但状态形状本身清晰，比"散落全局变量"高一档。

### 2.5 命名与目录约定：大体一致，三处例外

- core 命名一致；9 个页面 `data-page` 与文件名 100% 对齐；但"完全体"叫 `expert.html`、"进阶模式"叫 `advanced.html`——文件名按角色、标题按模式名，两套词汇并存。
- **死代码（零调用零测试）**：`core/hardware.py:72 clear_cache()`、`core/net.py:88 http_head()`、`core/update.py:45 check_lazy_update()`、`core/combos.py:150 get_combo()`。
- **仅靠"兼容"存活**：`schema.py:19 APP_VERSION="2.0"`（明令不许删）、`core/__init__.py:15-23` 的 9 条星号 re-export（几乎无人使用）。
- **判断**：一致度高于同类项目。真正隐患是**同义不同名**：`VERSION` 在 `schema.py:30` 是软件版本，在 `presetfile.py:51` 是格式版本（`1`）——这个重名已经造成真实 bug（见 2.7②）。

### 2.6 测试架构：后端分层到位，前端只有"实机层"

- **事实**：650 例 / 111 TestCase / 33 文件，与 `core/*.py` 近似 1:1；真起 ThreadingHTTPServer、真起子进程验脚本模式、真进程 + 真管道验 stdio；15 个文件用 `tempfile`、4 个用 `subprocess`；golden 快照 + 正则反向自检 + AST 依赖检查。
- **缺口**：① 前端 0 个 JS 单测（2394 行内联脚本只靠 CDP，在别的机器上会退化为"跳过"）；② `api.js ↔ ROUTES` 无一致性测试；③ `presets/export` 的 `app_version` 无断言。
- **判断**：后端测试按"层 + 真实边界"组织，不是按函数凑数；stdio 那组质量高于多数同类项目。"同构假绿"基本不存在——唯一镜像倾向是 golden 快照，但判据是行为 JSON。真正的假绿风险在前端。

### 2.7 文档-代码一致性：数字有门禁，行数与版本号没有

**① "界面不许直接 fetch('/api/')"——部分成立**
事实：`fetch('/api/` 只出现在 api.js，有静态测试守，这条真守住。但"走 API.xxx()"被普遍实现成 `API.get('/api/字面量')`（26 处）。**约定被"合规地绕过"，字面成立、意图约 45%。**

**② "版本号唯一来源 schema.VERSION"——已被破坏**
事实：`server.py:1002-1003` 在 `api_presets_export` 内 `from core.presetfile import (…, KIND, VERSION)`，局部名遮蔽了 `schema.VERSION`（`=1`），随后 `app_version=VERSION`。实测：

```
server.VERSION = 0.1.0
export → "app_version": "1"        ← 错
save   → preset.app_version = 0.1.0 ← 对
```

同一份预设，保存记 `0.1.0`、导出记 `1`；无任何测试覆盖。**判断：硬约束已在代码里失守，且肉眼与门禁都看不见。**（已登记为 T26）

**③ "不新增超 800 行文件"——无判据且已被违反**
- `grep 800 tools/verify.py` 零命中，tests 也无行数断言 → 约束没有任何判据。
- 当前超 800 行的源文件 **5 个**：`verify.py 3505`、`state.js 1414`、`server.py 1332`、`i18n.js 1162`、`schema.py 1104`。文档口径是 4 个 / verify.py 2651，差 854 行（+32%）。
- `i18n-zh2en.js` 自称"分两个文件是为了都不超过 800 行"，而 `i18n.js` 1162 行——文件在陈述一个已不成立的约束。
- **判断：文档承诺 > 代码现实。门禁对"数字"极严，对"规模"完全无感——这是这套体系最明显的选择性失明。**

## 三、改进建议（8 条，渐进式；均不触碰 T17 前提）

1. **修 `VERSION` 遮蔽 + 加一致性测试**（最便宜；已登记 T26）
   `server.py:1003` 改 `import core.presetfile as _pf`，用 `_pf.VERSION`；加测试断言 save 与 export 的 `app_version` 相等且 == `schema.VERSION`。约 10 行 + 1 测试。

2. **把 `server.py` 的应用层搬出去**（结构收益最大）
   新建 `webui/app.py`，把 39 个 `api_*` 原样搬过去，`server.py` 只留 `Handler`/`main()`/`log()` 并 re-export，保 `getattr(server,…)` 与测试零改动。`server.py` 可降到约 250 行。风险中低——脚本模式无包上下文，`app.py` 必须加同样的导入兜底，靠 `ScriptModeTest` 兜住。

3. **`schema.py` 按"变不变"拆，UI DTO 移出 core**
   ① 值域校验/DB→UI → `core/valuedomain.py`（UI 字段移 `webui/viewmodel.py`）；② settings → `core/settings.py`；③ 磁盘扫描 → `core/catalog.py`。每刀 re-export 过渡、逐刀提交、每刀跑全量。

4. **把"走 API.xxx()"变成判据**
   26 处字面量改具名方法；`test_frontend_transport.py` 增加双向一致性测试（从 api.js 抽 URL 与方法名，与 ROUTES 比对）；清理或标注 16 个无人调用的方法。

5. **`state.js` 先分区再分文件**
   按现有注释边界拆 `store.js`(12-189)、`widgets-combo.js`(602-890)、`subpreview.js`(892-1093)；第二步把 30 处 `APP.x =` 收进 `patch(partial)`。

6. **800 行约束上门禁 + 处理 `i18n.js`**
   `verify.py` 加 `check_sizes()`：>800 行只做白名单登记（文件名 → 当前行数上限），新增或增长即红。同时把 `i18n.js` 的 DICT 拆到 `i18n-dict.js`。

7. **给 T14 一个落地形态（后端语言感知）**
   新增 `core/i18n.py`（`msg(key, lang, **vars)`）+ `data/messages.json`（zh/en 两列）；`Request` 加 `lang`，前端 `invoke()` 统一带上；只迁 149 条对外可见文案。

8. **（可选，最后做）9 个页面内联脚本外链化**
   2394 行内联 JS 抽成 `page-*.js`，随后 CSP 去掉 `'unsafe-inline'`。成本高、风险中高，排在前 1–6 之后。

## 四、架构健康度评分表

| **分层** | **3 / 5** | core→webui 零反向依赖、core 内部无环值得满分；但应用层与 HTTP 适配同居 `server.py`，`api.py` 还反向 `getattr(server,…)`——分层只对了一半。 |
